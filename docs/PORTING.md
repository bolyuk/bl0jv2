# Портируемость VM: ESP32 и Raspberry Pi

Отчёт по состоянию на 2026-10-02. Цифры про размеры измерены на текущем коде; оценки скорости и трудозатрат — прикидки
и помечены так. Ничего из этого на железе не проверялось.

## 1. Что именно надо портировать

Только **виртуальную машину** (`bl0jv2-runtime`, 4,7 тыс. строк Java; из них интерпретатор `Bl0jv2_jVM` — 2,1 тыс.).
Компилятор (5,3 тыс.), линковщик, `DiskImport` и тесты остаются на хосте: ОС едет на устройство как готовый образ диска
с байткодом (`.bl0c`), на устройстве ничего не компилируется. Сам aeon-os (шелл, ФС, сеть, окна, скрипты) — это bl0, он
переносится без изменений.

Размер того, что должно уместиться (измерено):

| что | размер |
|---|---|
| байткод шелла (`sbin/shell.bl0c`) | 106 КБ |
| разделяемые библиотеки (`lib/*.bl0c`, 35 шт.; `fs` — 33 КБ) | ≈ 105 КБ |
| программы `bin/` | по 1–10 КБ каждая |
| образ диска целиком (свежая ОС) | 2 МБ, занято ≈ 0,35 МБ |

Байткод — только для чтения, его можно исполнять прямо из флеша/SD, без копирования в ОЗУ.

## 2. Что в дизайне уже помогает

- **Значения — 64-битные NaN-boxed слова**, регистры — плоский массив `long[]` (`NanBox`). Это сделано под C: тот же формат
  — `uint64_t`. Ссылки — индексы в таблицу кучи, а не указатели.
- **Инструкции фиксированной ширины**: 7 байт, опкод и три 16-битных операнда; 78 опкодов, 32 нативные функции
  (`NativeMethods`). Диспетчер — один большой `switch`.
- **Устройства уже за интерфейсом портов** (`PortDevice`): UART, диск (`BlockDevice`, сектор 512 Б), дисплей (ячейки
  текста), часы, NIC, общая папка. Гость говорит с ними через `in/out`, как с железом.
- **Собственный сборщик мусора** (`Collector`, 95 строк, mark-sweep по таблице слотов) и собственная куча (`Heap`) —
  от JVM-GC ничего не зависит.
- **Прерывания опросные**: проверяются каждые N инструкций в цикле интерпретатора, без сигналов — переносится как есть.
- **VM не касается файловой системы хоста** (по твоему правилу); хостовые «мосты» (сокеты, общая папка) — отдельный
  слой в `bl0jv2-cli`, а не часть VM.

## 3. Что в Java-реализации придётся переписывать, а не переводить

1. **Объекты кучи — это Java-объекты.** Строки — `java.lang.String` (UTF-16), массивы — `long[]` с размером, экземпляры —
   `long[]` полей плюс общий `Bl0jClass`, замыкания, кортежи, ошибки, события, мьютексы. В C нужен свой аллокатор,
   заголовок объекта (тип, размер, бит метки) и свои структуры. Это самая объёмная часть работы.
2. **Строки и Unicode.** `strSub`/`len` индексируют символы Java (UTF-16). В C надо выбрать представление: UTF-8 с
   индексом по кодовым точкам, или UTF-32. От выбора зависят память и скорость строковых функций (ФС и шелл на них
   стоят).
3. **Арифметика через таблицу операторов по Java-классам** (`OperatorTable`: `Integer`, `Double`, `String`, `Character`…
   — 25 регистраций, 200 строк). В C это диспетчер по тегу: просто, но надо повторить семантику точно, включая
   переполнение `int`, смешанные `int`/`double`, умножение строки на число, сравнение символа со строкой.
4. **Форматирование чисел.** `str(double)` и `'' + 1.5` дают Java-представление `Double.toString`. `printf("%g")` в C
   даёт другое; нужна реализация кратчайшего представления (Ryu/Grisu) и тесты на совпадение.
5. **Исключения.** Ошибки VM — Java-исключения и стек обработчиков в `CoreContext`. В C — явная раскрутка или
   `setjmp/longjmp`; `try/catch` самого bl0 работает через `handlerStack`, он переносится.
6. **Многоядерность.** Ядро = поток Java (`CoreWorker`), `ReentrantLock`, `ThreadLocal<CoreContext>`, события и мьютексы
   bl0 на `Condition`. На RPi — pthreads, на двухъядерном ESP32 — задачи FreeRTOS (по одной на ядро); на одноядерных
   (C3, ESP8266) VM работает с `-n 1`, как сейчас по умолчанию.
7. **Таймеры и сон** (`ScheduledThreadPoolExecutor`, `Thread.sleep`): заменяются таймером платформы.
8. **Сеть.** NIC виртуальный, стек TCP/IP/UDP/DNS написан на bl0 поверх кадров; наружу кадры выводит хостовый мост
   (`TcpOutboundBridge` и др. на Java-сокетах). На устройстве мост пишется заново поверх lwIP-сокетов (ESP) или
   Linux-сокетов (RPi) — по той же схеме «гость строит кадр, мост превращает его в реальный сокет». Настоящий L2 нужен
   только если захочется отдавать железу кадры напрямую.

## 4. Оценка по платформам

Размеры C-порта (прикидка): ядро интерпретатора 2–3 тыс. строк, куча/GC/строки/массивы/классы 1,5–2 тыс., нативные
функции 1–1,5 тыс., драйверы устройств 0,5–1 тыс. — вместе 6–9 тыс. строк C против 4,7 тыс. Java.

### Raspberry Pi

- **Pi 3/4/5 с Linux — порта почти нет.** Там работает OpenJDK: `java -jar` с текущей VM запустится как есть (ARM64).
  Ограничение — только вес JVM (десятки–сотни МБ ОЗУ, секунды запуска), но Pi 3 и старше с 1 ГБ справляются.
- **Нативный C-порт под Linux** (pthreads, сокеты, терминал через `termios`, диск — файл или SD как блочное
  устройство): средняя сложность, всё из п. 3 плюс тонкий слой хоста. Прикидка: 3–5 недель одного разработчика до
  прохождения всего набора тестов гостя. Даёт запуск за доли секунды и ОЗУ порядка единиц мегабайт.
- **Bare-metal на Pi** (без Linux, VM как «прошивка»): к порту добавляются загрузчик и старт ядер, MMU/кэши (без них
  интерпретатор в разы медленнее), UART PL011, SD (EMMC), кадровый буфер через mailbox, клавиатура (USB — самая тяжёлая
  часть) и сеть (Ethernet у Pi 4 — свой драйвер, Wi-Fi — закрытая прошивка). Прикидка: +6–12 недель сверху, и большая
  часть — драйверы, а не VM. Для текущих целей я бы не начинал с этого.

### ESP32

- **ОЗУ — главное ограничение.** ESP32 ≈ 320 КБ доступной SRAM, ESP32-C3 ≈ 400 КБ, ESP32-S3 512 КБ плюс опциональная
  PSRAM 2–8 МБ. Байткод (≈ 0,2 МБ) лежит во флеше и исполняется оттуда. Но куча VM — это объекты с 8-байтными
  значениями (массив из 100 элементов = 800 Б), строки и состояние шелла/ФС/сети растут, а порог сборки сейчас по
  умолчанию 64 МБ — его надо снижать до десятков КБ. Точного расхода ОЗУ полной ОС я не измерял; по ощущению, **полный
  aeon-os (шелл, ФС, сетевой стек, `wm`) без PSRAM не поместится**, а на **ESP32-S3 с PSRAM — поместится с запасом**.
  Урезанный профиль (ядро + шелл без сети/окон/скриптов, `lib/` по запросу) может работать и на 520 КБ — это надо
  мерить.
- **Скорость.** Интерпретатор на Xtensa 240 МГц — порядка нескольких миллионов инструкций в секунду (прикидка:
  5–15 M/с против 50–150 M/с на Pi 4). Шелл с командами в десятки инструкций будет отзывчивым; всё, что идёт через
  много слоёв bl0 (поиск по ФС, `sort` больших файлов, TCP-стек на каждый кадр), заметно медленнее, чем сейчас.
- **Устройства.** UART — родной; «диск» — раздел флеша или SD по SPI (512-байтные сектора, `BlockDevice` ложится 1:1,
  но флешу нужен износостойкий слой или хотя бы запись с проверкой); дисплей — SPI-LCD/OLED как текстовые ячейки или
  просто UART-терминал; сеть — Wi-Fi через lwIP-мост (п. 3.8); часы — RTC/SNTP.
- **Прикидка трудозатрат:** 4–6 недель до работающего шелла на ESP32-S3 (порт из п. 3 плюс ESP-IDF-обвязка и подгонка
  памяти); ещё 2–4 недели на урезанный профиль под ESP32 без PSRAM. ESP32-C3 и ESP8266 (80 КБ) для этой ОС слишком
  малы.

## 5. Что стоит сделать заранее, на Java, чтобы порт был дешевле

1. Вынести **спецификацию семантики** в тесты, не завязанные на Java: набор «байткод → ожидаемый вывод»
   (многое уже есть в `Bl0jv2_*Test`, но они гоняют исходники через компилятор; нужен режим «готовый `.bl0c` и золотой
   вывод»). Новый порт сможет проверяться без компилятора и без Java.
2. Зафиксировать **формат вывода чисел и правила Unicode** в одном документе (п. 3.2, 3.4) — это место, где порты
   расходятся незаметно.
3. Замерить **реальный расход кучи** шелла и типовых программ (счётчик живых слотов и байт в `Heap` уже есть) и
   выбрать цели по ОЗУ по факту, а не по оценке.
4. Убрать из `Bl0jv2_jVM` то, что мешает чтению как спецификации: разделить цикл интерпретатора, нативные функции и
   устройства по файлам (сейчас 2,1 тыс. строк в одном классе).
5. Решить заранее, нужен ли порт на **bare-metal** вообще: на Pi проще и надёжнее Linux + нативный порт, а «ОС поверх
   Linux» противоречит только духу, не задачам.

## 6. Рекомендация

1. Pi с Linux — запускать **уже сейчас** под OpenJDK, ничего не портируя.
2. Первый настоящий порт — **C-порт под Linux/Pi** (дешевле всего, даёт эталон на C и тесты из п. 5.1).
3. Затем **ESP32-S3 с PSRAM**, переиспользуя тот же C-код, меняя только слой платформы (потоки, таймер, диск, сеть).
4. Bare-metal на Pi и ESP32 без PSRAM — после того, как первые два пункта работают и есть замеры ОЗУ.
